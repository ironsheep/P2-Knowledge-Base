## Findings fixed

- **`setq_block_ops.yaml`:** "so the block transfer it starts completes first", "Keep transfers small for
  responsiveness" and "Interrupts delayed during transfer" go. The Silicon Doc says SETQ/SETQ2 shields the next
  instruction and must not be executing before an interrupt branch, and nothing about a long transfer.
- **`rep_instruction.yaml`:** "a branch, such as _ret_": SKIP's text calls `_RET_` an automatic branch; no source
  line says the same of a plain `ret`.

- **`fvar.yaml`:** a later CON constant compiles, so the limit reads "a label defined later". New proof
  `cp-027-fvars-later-constant.spin2`. The auditors recompiled the existing proofs, which could only confirm them;
  a compile-proven claim is tested on cases its proof did not include.

## Finding rejected

**"A pending interrupt is allowed to branch once REP is no longer active" as an inference.** The auditor held that
the Silicon Doc does not tie pending to REP. Its INTERRUPTS section does: "When an interrupt event occurs, certain
conditions must be met ... before the interrupt branch can happen", lists "REP must not be executing or active",
and then "Once these conditions are all met, any pending interrupt is allowed to branch." The same document also
says "Interrupts will be ignored during REP looping", and the KB now carries both, as the source does. The bench
ledger holds nothing on an interrupt arriving during REP, so this rests on the document, per Stephen's ruling.
