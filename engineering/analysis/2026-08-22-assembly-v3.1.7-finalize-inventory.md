## A. Contradicted claims — the co-release's owed sites

### A1 · F-303 — RGBI8 described as `2:2:2:2`, 16 colours
`part-iii/appendix-g-streamer-constants.md:115`

Prints: *"Read byte as RGBI 2:2:2:2 (16 colors + intensity)"*

**Authority (verified live this pass):** Silicon Doc `p2-documentation.txt:3800` —
*"RGBI8 mode uses the top three bits of the 8-bit pixel values as colors and the
bottom 5 bits as luminance values"*, with a `P[7:5] → Color` table of **eight**
colours. RGBI8 has no per-channel R/G/B fields.

Classification: **FABRICATED** (the source describes a different structure entirely).
Wrong twice over — the field split *and* the colour count.

**Correct looks like:** the framing already shipping in Debug Window v1.1.3
`ch04-bitmap.md:100` — *"Upper 3 bits select a color, lower 5 bits are intensity"*
(verified live this pass).

### A2 · F-305 — streamer DAC example with no pin setup
`appendix-g-streamer-constants.md:232-238` ("Audio DAC Output")

```
mov     mode, ##X_RFBYTE_1P_1DAC1 | X_DACS_3_2_1_0
```

No `WRPIN` DAC pin-mode, no COGID, no `DIRH`. The example cannot produce a voltage.

**Authority:** F-272's resolution — `%TT = %01` (`P_CHANNEL`), COGID in `M[3:0]`,
`DIRH` the pin, channel selected by the pin's low two bits. Corroborated on silicon
by **EF-054** (`%00` = 1,408 counts no-drive vs `%01` = 6,737) and **EF-055**.
`wrpin.yaml:54` documents the field.

**Correct looks like:** Streamer Guide v1.1.0 §11.0 (verified live this pass) — the
released, worked `cogid`/`setnib`/`wrpin`/`dirh` sequence.

**A2b — second defect in the same example, not previously enumerated.** The mode is
`X_RFBYTE_1P_1DAC1` — *one* DAC channel — but the routing is `X_DACS_3_2_1_0`, which
Appendix G's own line 196 defines as *"X3,X2,X1,X0 — one streamer word per channel
(standard 4-channel)"*. A 1-channel mode produces only X0; three of the four routed
channels have nothing to carry. Single-channel routing (`X_DACS_X_X_X_0`, X0 on DAC0
only) is what this example means. **Do not fix the pin setup and leave the routing.**

### A3 · F-308 — `X_PINS_ON` examples with no `DIRH`
`appendix-g-streamer-constants.md:228`, `:255`, `:289`

**Authority:** Silicon Doc — the streamer's pin data is OR'd with `{OUTB,OUTA}` to
produce *output states*; *"an I/O pin's output enable is controlled by its DIR bit."*
**Sealed on silicon as EF-062:** plain drive 8/8 · DIR low **4/8** · `DIRH` **8/8**.

The **no-`WRPIN`** half is correct and must survive: digital output needs no DAC mode,
no COGID, no channel. Only the missing `DIRH` is the defect.

**A3b — two sites the finding did not enumerate (review, not automatic).**
`appendix-g-streamer-constants.md:203` and `part-i/chapter-05-hardware.md:347` both
gloss `X_PINS_ON` as *"Enable pin outputs"*. The Silicon Doc's own wording is *"%e in
D[23] must be '1' to enable pin output"*, so the gloss tracks the source — but it is
the exact phrasing that let a reader conclude DIR was handled. Decide at fix time
whether to disambiguate ("enables the streamer's contribution to the pin's output
state"); do not reflexively rewrite a source-faithful line.

## B. NEW — the mode-table descriptions misdecode the naming convention

**Proposed ID: F-318** (register next-ID counter reads F-318; highest allocated F-317.)

**This is the finding-enumeration trap for the fourteenth time.** The register named
exactly one wrong row in this file's mode tables (F-303's `:115`). Re-deriving from
the artifact against the Silicon Doc, **31 further rows are wrong.**

**The rule.** Silicon Doc `part2-pixel-ops.txt:139-227` lists every streamer mode as
`<n>-pin + <k>-DAC<b>` — *n pins, k DAC channels, b bits per channel* — under column
headers reading literally `Pins | DAC Channels`. Appendix G's own "Mode Naming
Convention" section (`:275`) states the same rule: *"`_nP` Number of pins used ·
`_nDACn` Number of DAC channels, bits per channel."*

**The defect.** Every description reads `kDACb` as *"k pins, b DAC channels"* — the
channel count taken as a pin count, the bit width taken as a channel count. Where the
name carries an explicit `nP`, the description **ignores it** and uses `k` instead.
So `X_RFBYTE_8P_2DAC4` — 8 pins, 2 channels at 4 bits — prints as *"2 pins, 4 DAC
channels"*. The table contradicts the convention its own appendix documents 180 lines
below it.

**The `Value` column is correct throughout** — every encoding checks out against the
Silicon Doc. The encoding is sound; the prose gloss is what is wrong. This is a
description-only fix.

## C. Completeness gaps (unverified → decide: label or omit)

- **C1** — Neither the ADC nor the DDS/Goertzel table discloses that setting `D[19]`
  selects the other four-pin block. Carried from sweep plan §13 as a completeness
  caveat; never actioned.
- **C2** — `X_PINS_ON` (`:203`) and `X_WRITE_ON` (`:210`) are printed as two separate
  control flags with the **same value**, `%0000_0000_1000_0000 << 16` — because they
  *are* the same bit, D[23], whose meaning follows the mode's direction (`eppp` =
  pin-output enable on output modes; `wppp` = hub-write enable on capture modes).
  Correct as printed, opaque as presented. A reader OR-ing both gets one bit.
- **C3** — the Immediate→LUT rows (`:37-40`) gloss as *"N bits to LUT, b bits per
  pin"*. Silicon Doc `:143-146` reads *"imm → 32 × 1-bit LUT … 32 out"*: the b bits
  are the LUT **index** width, and the LUT's **output** is what reaches the 32 pins.
  Imprecise rather than contradicted.
- **C4** — the video/colour modes (`:114-118`) are all **24-pin** output per Silicon
  Doc `:191-195`; the table does not say so.
