## Why this document exists, and what it is not

The `release-yamls` **Step 8 survey** (commit `e14b9bcf`, recorded on the punch-list item
*"Review ALL manual content against the YAML-fidelity release"*) intersected each document's
`MANUAL-DESCRIPTOR.md` **declared source paths** against the release's changed files. That
answers *which documents touch changed ground* — seventeen of them, i.e. nearly all — which is
a **verdict, not a work list.** A path intersection cannot say what to write.

This pass asks the next question: **of the facts this release changed, which ones does each
document actually restate, and where.** Every row below is a located hit read in context, not
a name match. The probe set is the release's **reader-visible** change classes only — the
purge/repopulation, findability, schema-reshaping and reference-sweep classes changed nothing
a reader can observe and are correctly absent here.

**Grades.** 🔴 **CORRECTION** — the document states something the shipped KB now contradicts;
a reader acts on it and is wrong. 🟡 **ALIGN** — not false, but behind its own source: an
unlabelled limit, a missing caveat, a figure the KB has since sourced or measured.
🟢 **ENHANCE** — no defect; new KB coverage the document could now carry.

## 🔴 CORRECTIONS

### ALM-1 · The mislabel, in the Assembly manual's own feature list
`part-i/chapter-05-hardware.md:231`
> "**Configurable I/O circuitry:** Programmable pull-up/down resistors, output drivers, and
> high-impedance (floating) modes"

**The P2 has no programmable pull-up/pull-down resistors.** This is the exact class the sprint
started from (§1.4), in the manual's own capability summary. `P_HIGH_*`/`P_LOW_*` select
**drive strength**.

**What to write** is *not* a deletion — §1.24 settled that. A reader **can** pull a line high
or low: `P_HIGH_15K` with `DIR=1, OUT=1` is a 15 kΩ resistive path to VIO, and the Silicon Doc
uses that vocabulary for these same rungs (`silicon-doc-text.txt:4599`). The one difference
that breaks code is that the pull is a property of **driving**, so **DIR must stay high**.
Source: `architecture/pin-drive-configuration.yaml`, `language/{pasm2,spin2}/concepts/basic-io.yaml`.

### ALM-2 · ADDSX's C-flag prose contradicts its own Operation line
`part-ii/instructions-a.md:228`
> "the C flag is set (1) if the result is negative (**Result[31] = 1**)"

Its own Operation line at `:208` and its encoding row at `:219` both say **`C = true sign of
(D + S + C)`**. `Result[31]` and the true sign **differ exactly on overflow**, which is the
condition `TJV` exists to detect. This is **F-379** — the KB repaired precisely this in
`language/pasm2/{addsx,subsx}.yaml` this release.

The family is otherwise correct in ALM: `ADDS` `:169`, `SUBS` `:1223`, `SUBSX` `:1254`,
`CMPS` `:387`, `CMPSX` `:470`, `SUMC` `:1321` all carry the true-sign form. **ADDSX is the lone
outlier** — which is the F-379 lesson repeating: a class sweep that misses one member leaves a
defect that looks deliberate because every neighbour is right.

*Same paragraph, lesser:* `:191` (ADDS) writes "the true sign of the signed sum, Result[31] = 1"
as if the two were the same thing. They are not. It recovers ("C carries the true sign… it is
not a signed-overflow indicator"), so fix the parenthetical, not the paragraph.

### ALM-3 · GETBRK's flag effect is required, not optional
`part-ii/instructions-g.md:14, :19`
> `**GETBRK**  *Dest*  **{WC|WZ|WCZ}**` … "WC, WZ, or WCZ are **optional** effects"

The shipped KB (`language/pasm2/getbrk.yaml:13`) states: *"GETBRK **REQUIRES** a flag effect
(WC, WZ, or WCZ); the no-flag form does not assemble."* Each flag selects a **different**
result. This is **F-368**.

**The P2 Interpreters & Emulators Guide already has it right** — `xbyte-body.md:1193`: *"It
requires a flag effect, and the flag you choose selects which information you get."* That is
Chip Gracey's own CG-3 correction. So the two shipped manuals **disagree with each other**, and
the braces in ALM's syntax line are wrong as well as the prose.

### ALM-4 · The clock row attributes to the datasheet two figures it does not contain
`front-matter.md:144` and its footnote at `:153`
> "| Clock | 80 MHz | 180 MHz recommended; **250 MHz typical overclock; 350 MHz absolute max**¹ |"
> "¹ **Per P2 Datasheet.** Higher frequencies require adequate thermal management."

The P2 Datasheet's AC Characteristics PLL row gives **min 3.33 / typ 180 / max 320 MHz**
(`p2-datasheet-text.txt:2200`, footnote 2 at `:2209`: *"Nominal PLL frequency … is 180 MHz at
up to 105 degC"*). It contains **neither 250 MHz nor 350 MHz**.

- **250 MHz "typical overclock"** — no source we hold.
- **350 MHz** is real but is **not** an absolute maximum and **not** from the datasheet: it is
  the **VCO/1 overclock ceiling** from the Silicon Doc (`part3-interrupts.txt:545`, *"For
  fastest overclocking, the PLL can be pushed to 350 MHz using the 'VCO / 1' mode (%PPPP = 15)"*).
  `architecture/clock_system.yaml:209` states the distinction outright: *"350 MHz is the
  absolute VCO/1 overclock ceiling… PLL output max = 320 MHz (180 MHz typical)."*
- **The datasheet's actual 320 MHz maximum is absent from the row entirely.**

**And the manual contradicts itself:** `part-i/chapter-04-timing.md:94` says *"a system clock
that can run up to 320 MHz"*, with `:96`, `:562` and `:655` all computing from 320. The front
matter says 350 is the absolute max; chapter 4 says 320 is the ceiling.

This is the **whose-limit** rule (E-007): every clock figure must name whether it is the
compiler's, the datasheet's, or an overclock ceiling. `ch04:34` already does this correctly
("the PLL can be pushed to 350 MHz using VCO/1 mode (%PPPP = 15)") — copy that discipline up.

### IOSP-1 · The input threshold is stated as fixed volts; it is a fraction of the supply
`part-3-input-modes/chapter-12-digital-input.md:25` and `:95`
> "pins operate as standard CMOS inputs with **approximately 1.65V threshold**"

This is **F-407**'s shape exactly. The purge removed a fabricated `VIL 0.8 V / VIH 2.0 V /
~1.5 V threshold` block from `io_pin_timing.yaml`, and the real table — the P2 Datasheet's **DC
Characteristics**, p.47-48 — was in a source the file already cited:

| Symbol | Parameter | Value | Line |
|---|---|---|---|
| `Vih` | Input Logic Threshold | min `Vxxyy*0.3` · typ `*0.5` · max `*0.7` | `:2163` |
| `Vdd` · `Vxxyy` | Supply ranges | 1.7/1.8/1.9 V · 3.15/3.3/3.45 V | `:2159`, `:2161` |

**The datasheet states one threshold as a fraction of the I/O supply.** At 3.3 V that is
**0.99 / 1.65 / 2.31 V** — so 1.65 V is the *typ* value and the real band is ±0.66 V wide, and
**it moves with `Vxxyy`**, so two pin groups on different supplies do not share thresholds.
Writing "approximately 1.65V" hides both the tolerance and the supply dependence.

*Same class, same chapter:* `:156` gives `threshold_voltage = (level / 256) × 3.3V` for the
programmable level comparator — that genuinely **is** a fraction of VIO, so hard-coding 3.3 V is
wrong for any other supply. `:130`, `:133` and `:583` derive the ~1.4 V TTL level from the same
hard-coded 3.3 V.

### IOSP-2 · The `P_HIGH_15K | P_LOW_FLOAT` composition — F-356, still live
`part-1-fundamentals/chapter-02-enhanced-direct-io.md:94, :399, :439, :480`
> `WRPIN(pin, P_HIGH_15K | P_LOW_FLOAT)     ' 15kΩ pull-up, no low drive`

Four sites, exactly the count F-356 recorded. **No Parallax source states this composition.**
F-356 is still `CONFIRMED`.

⚠ **§1.24 changed what the repair is.** Calling `P_HIGH_15K` a "15 kΩ pull-up" is now
*acceptable vocabulary* — the KB stopped policing a word its own authority uses. What is owed
here is (a) a source for the composition or its removal, and (b) the **DIR caveat** at each
site. Anyone scoping F-356 off its original wording will do the wrong repair.

*Scope note:* pull-vocabulary appears on **48 lines across 7 IOSP files**
(`ch02` 13 · `ch06` 9 · `ch12` 16 · `ch19` 1 · `app-b` 7 · `app-a` 1 · `index` 1). F-356's
23 mislabel + 5 internal-pull-up assertions are the subset inside that; the rest are legitimate
external-resistor and USB references. Do not sweep by word count.

### AN001-1 · The clock pitfall states a maximum that exists nowhere
`P2AN001.md:638`
> "The P2's **specified maximum is 300 MHz**; the original research code ran at 320 MHz,
> **which is over spec.**"

**300 MHz appears in no source we hold and in no KB file.** The datasheet maximum is **320 MHz**
— so the research code was **at** the datasheet limit, not over it, and the note tells the
reader otherwise.

**This note now contradicts its own shipped YAML companion.** `application-notes/p2an001-…yaml`
was corrected on 2026-09-09 and reads: *"the AC characteristics give the PLL system clock as
min 3.33 MHz / typ 180 MHz / max 320 MHz, with the footnote 'Nominal PLL frequency (system clock
speed) is 180 MHz at up to 105 degC'."* The four-artifact model requires the note and its
companion to agree.

### AN001-2 · The 15 mV figure is now measured, and 15 mV must not be quoted as a spec
`P2AN001.md:626`

The note qualifies 15 mV correctly as designer-stated. But the companion moved further:

> "Hardware-verified 2026-07-07 on real P2: the ratiometric single-pin absolute error was
> **≤9 mV**, reproducible… NOTE: the wider '~15 mV pin-to-pin spread' figure is a designer report
> that **the bench has NOT yet reproduced**… **Do not quote 15 mV as a specification.**"

The note carries the unreproduced figure and not the measured one. Empirical sources are
first-class here and outrank a designer report.

### AN002-1 · The CORDIC issue interval is not a fixed eight clocks
`P2AN002.md:367` (and `:235`, `:328`)
> "each cog gets a turn **every eight clocks**" · "a cog can issue **every 8 clocks**"

The companion now quotes the authority: *"Cogs can start CORDIC operations **every 1/2/4/8/16
(#cogs) clocks** and get results 55 clocks later."* The interval **depends on how many cogs are
running**; 8 is one case, not the rule. The 55-clock latency is fixed and the note has that right.

## 🟡 ALIGN

- **ALM-5** `part-i/chapter-04-timing.md:20` — "180 MHz typical, **320 MHz extended per the spec
  sheet**". 320 is the datasheet **absolute maximum**, not an "extended" mode. Label it.
- **ALM-6** `appendix-d-special-registers.md:11-12`, `appendix-h:430-431`,
  `special-registers.md:142, :170` — `$1F6`/`$1F7` read *"Multi-purpose register A/B"*, which
  names **neither role**. **F-363** corrected the KB's byte-identical rows to *"CALLD-imm return,
  CALLPA parameter"* / *"…CALLPB…"*. Adopt that wording.
- **IOSP-3** `chapter-07-pulse-transition.md:271` — *"the P2 datasheet gives a rated 180 MHz; the
  Silicon Documentation notes a practical ceiling around 350 MHz."* Both halves are sourced, but
  the **datasheet's 320 MHz PLL maximum is missing between them**, so the reader sees 180 and 350
  and infers the wall is 350. Give all three tiers with their owners.
- **IOSP-4** `part-5-appendices/appendix-b-p-constants.md` + `ch02:51,66` — the drive-strength
  table is correct (30 mA / ~17 Ω); add the DIR caveat where `P_HIGH_15K` is presented, per §1.24.
- **DeSilva-1** `COMPLETE-OPUS-MASTER.md:2881` — *"No pullup/pulldown **by default** — Use
  external resistors or **configure smart pin modes** (advanced topic)."*

  ⚠️ **This re-adjudicates a site F-356 closed.** F-356 (2026-08-25) states it *"was checked and
  left because it is already **correct**."* Against the framing in force that day, it was. **Ledger
  §1.24 (2026-09-09) changed the framing**, and under it this line is weak in two ways: "by
  default" implies a **non-default internal pull exists**, and it sends the reader to **smart-pin
  modes** when the mechanism is **drive strength**. §1.24's answer-first order applies — you *can*
  pull a line high or low; `P_HIGH_15K` with `DIR=1, OUT=1` is a 15 kΩ path to VIO; **DIR must stay
  high** because the pull is a property of driving. Graded 🟡, not 🔴: nothing here makes a reader's
  code fail, and F-356's own disposition is the reason it reads as settled.

  (`:294` — *"a floating pin has no opinion"* — is correct and stays.)
- **AN001-3** `P2AN001.md:555, :562, :628` — "input resistance ~500 kΩ". The companion **removed**
  this under cite-or-omit. The note hedges it well ("only approximately known… calibrate it"), so
  this is a sourcing decision, not a falsehood: cite it or drop the number and keep the calibration
  instruction.
- **AN002-2** `P2AN002.md:354, :369` — "about **28 bits** of precision" for trig. The companion's
  `verify: Precision ~28 bits` flag was removed as uncited. Same disposition as AN001-3.
- **AN002-3** — the companion added a scope qualifier to EF-053: *"this measures **WHERE** results
  are lost, not why; state it as the tested shape — keep hub access out of both loops — not as a
  law about any hub access."* Check the note's pitfall does not generalise past that.
- **AN003-1** — the companion now says *"**No ENOB/SNR/THD figure is stated by any source and none
  is asserted here.**"* Confirm the note asserts none.
- **AN004-1** — `P2AN004.md:78, 89, 92, 104, 108, 115, 119, 328` build on `P_OE | P_LOW_FLOAT`.
  Different composition from IOSP-2 and correctly explained as drive-when-high/float-when-low, but
  it needs the same sourcing question asked of it.
- **Torture-1** `P2-Layout-Torture-Test.md:727` — `P_OE_FLOAT_LOW_1K5_PULLUP_FILTER` is not a real
  constant. It is a deliberate line-wrap stressor in an instrument, not a publication — but a
  fabricated constant name in any document is worth a real long symbol instead.

## 🟢 ENHANCE — new KB coverage no manual carries

- **`-1` is not a synonym for `NEWCOG` (F-390).** Every manual and app-note uses `NEWCOG`
  correctly and **no document uses `-1`** — so there is no defect. But the KB now explains the
  trap, cited and confirmed against emitted bytecode: `-1` arrives as `$FFFF_FFFF`, decodes
  `D[5:0]=%111111`, and **launches an even/odd cog pair**. A reader meeting `coginit(-1, …)` in
  community or P1-shaped code has nowhere to look. Natural homes: Getting Started (cog-launch
  section), DeSilva, ALM `COGINIT`.
- **The smart-pin state/config separation (F-369).** *Each smart pin holds 126 bits of state
  separate from its WRPIN configuration* — in the Silicon Doc, carried nowhere in the KB until
  this release. IOSP `chapter-03-smart-pin-architecture.md:78` says the registers "are
  initialized according to the mode" without the separation or the figure. This is the DIR-reset
  mechanism the whole configure-while-DIR=0 rule rests on.
- **Event source numbers.** ALM `chapter-05-hardware.md:361-376` tables eleven event sources with
  **no number column**, and `:395` tells the reader `SETINT1/2/3` take a "4-bit code in Dest[3:0]"
  without ever giving the codes. The KB now has the sixteen correctly enumerated (and ATN
  corrected from 15 to **14**). The manual is not wrong — it does not answer the question.

## Clean — verified, so the sweep does not spend time here

Each was probed and read, not assumed:

- **`150 mA` per pin never propagated.** Every drive figure in ALM and IOSP reads **30 mA**,
  which agrees with the datasheet's ±30 mA absolute maximum and with `Vol`/`Voh` stopping at 30 mA.
- **No TTL logic levels anywhere.** No `VIL`/`VIH`/`VOL`/`VOH` or 0.4/2.4 V figures in any
  document. (Every `2.0V` hit is a `P_DAC_*_2V` constant.)
- **The interrupt vector map is correct in ALM** — `$1F0=IJMP3` … `$1F5=IRET1`
  (`appendix-d:5-10`, `appendix-h:424-429`, `special-registers.md:29-136`, `ch05:395`). The
  published KB's inversion never reached it.
- **`WRLUT` operand order is correct** — `instructions-w.md:689-700`: Dest is the value, Src is
  the LUT address.
- **LUT sharing direction is correct** — `instructions-s.md:427, :441`: writes in the adjacent
  companion cog are copied to *this* cog's LUT.
- **`LOCKTRY` acquires** everywhere it appears; no "query" form survives.
- **No fabricated mnemonics** — `RDCOGID`, `RDLUTS`, `NIXINT0`, `TRGINT0` appear in no document.
- **No boot-ROM font or math tables.** No document claims the fabricated residents; ROM mentions
  are the booter, the Xoroshiro seed, and auto-baud.
- **No `WAITMS` ceiling stated anywhere** — only usage, so the 400× error had nothing to infect.
- **No `P_LEVEL_B` / `P_SCHMITT_B`** in any document.
- **TAQOZ's "early version" (F-370)** touches nothing — TAQOZ appears in no manual body.
- **The shipped example corpus is clean.** Of 95 `examples-library/*.spin2` files, **none**
  carries a pull idiom or a `-1` cog launch. The hits are all under `REF/` and `research/` —
  third-party reference code, not ours.
