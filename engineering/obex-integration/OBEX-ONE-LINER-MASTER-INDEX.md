# OBEX One-Liner Master Index

**Status:** proposed — awaiting audit and Stephen's review
**Date:** 2026-10-11
**Finding:** F-573 (`engineering/operations/P2KB-CORRECTION-FINDINGS.md`)

## Purpose

This worksheet proposes one single-line description for each of the 130 OBEX objects in the P2 Knowledge Base
(`deliverables/ai/P2/community/obex/objects/[0-9]*.yaml`). The line is meant to be kept in
`functionality.description_short`. p2kb-mcp shows that field as `description` in every OBEX lookup and in every
OBEX search list, so it is the one line an AI agent reads about each object.

This draft replaces an earlier one that was written from a damaged copy of the catalog. It is written from the
object YAMLs as they now stand, which mirror their OBEX catalog pages. Only these fields were used:
`object_metadata.title`, `author`, `functionality.description_full` (the catalog description, full text),
`functionality.category`, `functionality.tags`, `technical_details.content_type` (Code / Hardware / Tip),
`technical_details.languages` and `technical_details.microcontroller`.

The fifth column is the catalog description (`functionality.description_full`). Line breaks and runs of
whitespace are collapsed to single spaces. When the text is over 300 characters, the column shows the first 300
characters followed by ` …[N chars]`, where N is the length of the whole collapsed text. A `|` inside a cell is
written `\|`. A `—` in the Category column means the catalog lists no category.

## Rules for each proposed one-liner

1. One sentence of at most 120 characters. It ends with a period and is never cut mid-word.
2. It uses only facts that the title, category, content type or catalog description state. It adds no
   capability, chip, protocol, platform or count that the catalog does not state. When the catalog says P1, the
   line keeps P1. When the content type is Hardware or Tip (PCB files, 3D models, tips), the line says what the
   item is and does not call it a driver.
3. No evaluation or marketing words, even when the author uses them (robust, high-performance, full-featured,
   easy, powerful, optimized, fully qualified, set-and-forget, best …). No compile or working status. No licence
   talk. No URLs. No contact details for any person.
4. Technical terms and part numbers are kept exactly as the catalog writes them. Only obvious typos and
   word-joins are fixed, and only in the line itself.
5. The line leads with what the object is or does. It does not start with "This object" and does not repeat
   the title verbatim.
6. When the catalog description is long, the line summarises its opening purpose only. It lists no features
   beyond what fits.
7. When the catalog says nothing usable, the line is written from the title and category, and the cell begins
   with `[title-only] `.

## Notes

### What changed from the superseded draft

- **No `[title-only]` rows.** All 130 catalog descriptions now say something usable. The earlier draft's
  garbled `<Overviewn McPhalen.` text (2839, 2843, 2846, 2851, 2853) and its generic "Utility object for P2
  development." text (17 objects) were scrape damage. The real catalog text replaced both, and every line in
  those rows was rewritten from it.
- **No cut-short texts.** The earlier draft listed texts that stopped at about 300 characters (3804, 4064,
  4068, 4257, 4266, 4267, 4571, 4581, 4597, 4720, 4858) or began mid-word (4442, 4758). Every one is now whole,
  and the `[N chars]` counts in the table are the full lengths.

### Objects whose catalog record disagrees with itself

None of these is fixed in a line. Each line uses only what both parts of the record agree on, or what the
description states.

- **5274 (PING+).** The description says the object is for these sensors "with the P1". The record lists
  microcontroller P2 and language SPIN2. The line names no chip.
- **4571 (180° TOF Sensor).** The description names the I2C I/O expander "PCV8575" once and "PCF8575"
  three times — the catalog's own text. The line leaves the expander out.
- **4894 (FRSW and FAT32 for P2).** The title says "FRSW". The description says "FSRW". The line uses the
  description's "FSRW".
- **2822 (DS3231) and 4808 (mcp2517).** The descriptions say P1 and P2, and the catalog lists both
  microcontrollers (`[P1, P2]`). The lines say P1 and P2.
- **2846 and 2870 (Sony IRCS Rx).** These two objects have the same title, the same author and the same
  description. Only the category differs (Protocol and Human Input). Their lines are identical. Two agents
  searching for an IR receiver will see two entries that read the same. Whether OBEX lists one object twice is
  a question for the catalog, not for this line.
- **2828 (Soft Timer).** The category is Sensor, but the object is a timer. The line follows the description.
- **2858 (MAX7219 Dot Matrix).** The languages field is "Generic". The description says "Language Spin2" and
  "spin object". The line says "Spin object".

### Judgement calls worth checking

- **Hardware and Tip rows.** 4864, 4898, 4899, 4905 and 5096 are Hardware. Their lines describe files, models
  or a library. 4917 is Code and Tip, and its line begins "Tip showing …".
- **4899 (P2-EVAL 3D Model).** The description says Parallax 3D Models are *typically* in STEP and VRML formats.
  It does not say this entry contains both. The line keeps "typically".
- **4254 (eInk Driver).** The description says displays "sold by Parallax.com or by Mikroe.com". The line says
  "Parallax or Mikroe", so that no domain name appears in a served line. "A working driver" was dropped (rule 3).
- **4926 (PNut/Spin2 v55).** Apart from links, the only text is the v55 change note. The line is built from the
  title and that note. The line will go stale when the catalog entry moves to a later version, as the title will.

### How the columns were produced

The first five columns were built with a single `mawk` command over the 130 object files. It collapses
whitespace, removes YAML quoting (including the escaped line breaks in the double-quoted texts of 4442, 4718
and 4889), and counts characters rather than bytes. A second `mawk` command compares those five columns in
this file against the YAMLs: 130 of 130 match. A third checks every one-liner for length (120 or fewer),
a final period and the column count.
