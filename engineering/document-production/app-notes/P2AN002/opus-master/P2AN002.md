## Abstract

The P2 has a hardware math solver — a CORDIC engine, shared by every cog — that turns operations a software library would spend hundreds of instructions on into a single instruction with a fixed, known latency. Rotate a point, convert between cartesian and polar, take a sine, a logarithm, a square root, a full 64-bit multiply or divide: each is one operation you hand to the solver and one you read back. This note shows how to use that solver for real work — distance and heading, rotation, waveform synthesis, fixed-point scaling — and how to keep it busy enough to get a result every eight clocks when you have a lot to compute.

*What you'll build: a handful of short, runnable programs — each a complete CORDIC technique — that stream their results to a DEBUG window you can check against exact, known answers.*

## Prerequisites & Hardware

You should already be comfortable with:

- Reading and writing Spin2, and reading PASM2 (the throughput recipe and the capstone are in assembly).
- Starting code in another cog with COGINIT (the pipelining recipe uses a second cog).
- The P2's 32-bit signed integer model. The CORDIC works in integers and fixed-point; there is no floating-point hardware here.

For the full instruction-level reference — every operand, every flag — this note points to the **PASM2 reference** and the Spin2 documentation rather than reproducing them. It *uses* the solver; it does not re-enumerate it.

**Hardware:**

- Any P2 board (P2 Edge or P2 Eval).
- **Nothing else.** Every recipe verifies in a DEBUG window against a closed-form answer — the CORDIC computes exact, deterministic math, so you confirm a build by comparing its output to arithmetic you already know, with no bench instruments at all.

## The Idea

Most processors compute a sine or a rotation in software: a polynomial, a table, a loop. The P2 instead has the operation built into the hub as a **54-stage pipeline**. You do not call a function — you **issue** an operation, go do other work, and **retrieve** the result a fixed number of clocks later.

That shape — *queue, work, retrieve* — is the one idea under everything in this note. It has three consequences worth holding onto before any detail:

- **The result is not instant, but its timing is exact.** When a cog issues a CORDIC operation, the result is available a fixed **55 clocks** later. You can spend those clocks on anything; the answer will be waiting.
- **Angles are a full 32-bit circle.** The CORDIC measures angle as an unsigned 32-bit number where the whole circle is 2³², so `$0000_0000` is 0°, `$4000_0000` is 90°, `$8000_0000` is 180°, and `$C000_0000` is 270°. There is no degrees-or-radians choice and no range to wrap by hand: angles add and subtract modularly, and overflow *is* wrap-around. This single convention is what makes rotation arithmetic so clean on the P2.
- **Two ways in.** From Spin2 you call built-in methods (`ROTXY`, `XYPOL`, `QSIN`, …) and the interpreter manages the queue-and-retrieve for you. From PASM2 you issue the instruction (QROTATE, QVECTOR, …) and read the result yourself with GETQX / GETQY — which is what lets you overlap operations for throughput. Use Spin2 for most work; reach for PASM2 when you are processing a lot of data and want the pipeline full.

## How It Works (in brief)

The solver offers eight operations. The full encoding of each lives in the PASM2 reference; this is the working summary.

| Operation | PASM2 | Does |
|---|---|---|
| Multiply | QMUL | 32 × 32 → 64-bit unsigned product |
| Divide | QDIV | 64 ÷ 32 → quotient + remainder |
| Fractional divide | QFRAC | 64 ÷ 32 → fractional quotient |
| Square root | QSQRT | √ of a 64-bit value → 32-bit root |
| Rotate | QROTATE | rotate (X, Y) by an angle |
| Cartesian → polar | QVECTOR | (X, Y) → (length, angle) |
| Integer → log₂ | QLOG | 32-bit value → 5.27 fixed-point log |
| log₂ → integer | QEXP | 5.27 fixed-point → 32-bit value (antilog) |

In PASM2 the pattern is always the same — issue, then read:

```pasm2
                qmul    base, scale     ' queue a 32x32 multiply
                ' ... up to 55 clocks of other work ...
                getqx   prod_lo         ' low  32 bits of the product
                getqy   prod_hi         ' high 32 bits
```

GETQX and GETQY wait for the result if it has not arrived yet, so a single operation needs no timing care — the cog simply stalls until the answer is ready. If you read when nothing was ever queued, the read returns in two clocks and sets the QMT (CORDIC-empty) event, which is how you catch a missing-issue bug.

From Spin2 the same operations are methods that return their results directly, with the queue-and-retrieve hidden:

```spin2
  x, y         := ROTXY(x, y, angle)    ' rotate a point
  length, angle := XYPOL(x, y)          ' cartesian -> polar
  s            := QSIN(length, angle, 0) ' length * sin(angle)
```

Two facts set the throughput ceiling, and Recipe 6 builds on them: a cog can issue one CORDIC operation **every eight clocks** (its hub-access window), and the pipeline is 54 stages deep. Because the pipeline is far longer than the issue interval, a cog can keep **several** operations in flight at once — roughly seven (the 54-stage depth divided by the 8-clock window) — issuing a new one each window while reading the matching earlier result. That is how you get one finished result every eight clocks instead of one every 55.

## Choosing a Technique

The recipes below are independent — each is a complete program for one job. Pick by what you need:

| If you need… | Use | The operation |
|---|---|---|
| Distance and direction between two points | **Recipe 1** | QVECTOR / `XYPOL` |
| To rotate a point about the origin | **Recipe 2** | QROTATE / `ROTXY` |
| To place points around a circle / arc | **Recipe 3** | `POLXY` |
| A sine or cosine wave | **Recipe 4** | `QSIN` / `QCOS` |
| 64-bit-safe scaling, magnitude, log/exp | **Recipe 5** | `MULDIV64`, QVECTOR, QLOG/QEXP |
| To transform a lot of data fast | **Recipe 6** | any op, pipelined |
| A real-world reference design | **The Ceiling** | three-phase motor control |

Each recipe ends with a 🔍 **Verify** that compares the DEBUG output to a number you can work out by hand.

## Recipe 1 — Distance & Heading

**Use it when** you have two points and need *how far apart* and *in what direction* — the navigation primitive behind "steer toward the target," range-and-bearing, and vector magnitude.

A single QVECTOR operation (the Spin2 `XYPOL` method) converts a cartesian vector into polar form: it returns the vector's **length** and its **angle** at once. Feed it the difference between two points and you have distance and heading from one call.

```spin2
CON
  _clkfreq = 200_000_000

PUB main() | dist, heading, dx, dy
  dx := 3
  dy := 4
  dist, heading := XYPOL(dx, dy)        ' (x,y) -> (length, angle)
  debug("distance=", sdec(dist), "  heading=", uhex_long(heading))
```

**How this works.** `XYPOL` takes the vector `(dx, dy)` and returns its length and its angle. The length is an ordinary integer in the same units as the inputs; the angle is a 32-bit binary angle (the convention from The Idea). For a real navigation problem `dx`/`dy` are `target - current` on each axis, and the heading drops straight out — no `atan2` library, no quadrant bookkeeping, because the binary angle already spans the full circle.

🔍 **Verify:** With `(3, 4)` the DEBUG window shows **distance = 5** — the 3-4-5 triangle — and **heading ≈ `$25C8_xxxx`**, which is about 53°, exactly atan2(4, 3). Change the inputs to `(0, 100)` and the heading becomes `$4000_0000` (90°, straight up); `(-100, 0)` gives `$8000_0000` (180°).

## Recipe 2 — Rotate a Point

**Use it when** you are turning coordinates: spinning a sprite, re-framing a sensor reading, stepping around an orbit.

QROTATE (the Spin2 `ROTXY` method) rotates a point `(x, y)` about the origin by a binary angle and returns the rotated point.

```spin2
CON
  _clkfreq = 200_000_000

  QTR = $4000_0000              ' 90 degrees as a 32-bit binary angle

PUB main() | x, y
  ' Rotate the point (100, 0) by 90 degrees about the origin.
  x, y := ROTXY(100, 0, QTR)
  debug("x=", sdec(x), "  y=", sdec(y))
```

**How this works.** `ROTXY` computes the rotation `(x*cos(T) - y*sin(T), x*sin(T) + y*cos(T))` in hardware. Because the angle is a binary angle, a turn is just an add: to rotate a little further each frame, add a constant to the angle and let it wrap. To rotate the *other* way, subtract — or add the two's-complement angle, which is the same thing.

💡 **Tip:** `ROTXY` rotates the whole vector, so it is also your fastest way to compute a sine *and* cosine of the same angle scaled by a radius: rotating `(radius, 0)` by the angle gives `(radius*cos(T), radius*sin(T))` in one call.

🔍 **Verify:** Rotating `(100, 0)` by 90° gives **`(0, 100)`** — the point swings from the +X axis up to the +Y axis. Rotate by `$8000_0000` (180°) instead and it lands at `(-100, 0)`.

## Recipe 3 — Draw a Circle

**Use it when** you want points laid out around a circle or an arc — a dial, a radar sweep, a round gauge, evenly-spaced positions.

`POLXY` is the inverse of Recipe 1: it takes a **length and an angle** and returns the **cartesian point**. Step the angle in equal increments and you walk the circle. Here the points stream to a DEBUG `PLOT` window so you can watch the circle draw itself.

```spin2
CON
  _clkfreq = 200_000_000

  R       = 100                 ' circle radius
  STEPS   = 64                  ' points around the circle (even)
  ASTEP   = $8000_0000 / (STEPS / 2)   ' one full 2^32 circle / STEPS

PUB main() | i, ang, x, y
  debug(`PLOT myplot size 240 240 origin 120 120 dotsize 4)
  repeat
    repeat i from 0 to STEPS-1
      ang := i * ASTEP                    ' fraction of a full 2^32 circle
      x, y := POLXY(R, ang)               ' (length,angle) -> (x,y)
      debug(`myplot `(x, y))
    waitms(500)
```

**How this works.** A full circle is 2³² binary-angle units, so `STEPS` equal steps are `2^32 / STEPS` apart. That value would overflow a 32-bit constant written directly, so it is formed as `$8000_0000 / (STEPS / 2)` — half the circle divided by half the steps, the same quotient without the overflow. Each `POLXY(R, ang)` places one point at radius `R`; stepping `ang` around the full range walks the whole circle.

🔍 **Verify:** The `PLOT` window draws a clean circle of 64 dots, centered on the origin marker, radius 100. If you see an *ellipse*, your X and Y plot scales differ; if you see an *arc* instead of a full circle, `ASTEP` and `STEPS` disagree.

## Recipe 4 — Sine & Cosine

**Use it when** you need a waveform or an oscillator: tone generation, LFOs, dimming curves, any "smoothly varying" value.

`QSIN` returns `length * sin(angle)`; `QCOS` returns `length * cos(angle)`. Sweep the angle and you have a sine wave, scaled to whatever amplitude you pass as `length`.

```spin2
CON
  _clkfreq = 200_000_000

  AMPL  = 1000
  ASTEP = $0200_0000            ' angle increment per sample

PUB main() | ang, s
  debug(`SCOPE sine size 400 200 samples 256 rate 1 pos 100 100)
  debug(`sine 'sin' -1100 1100 180 20 15 CYAN)
  ang := 0
  repeat
    s := QSIN(AMPL, ang, 0)     ' AMPL * sin(ang); 0 -> full 2^32 circle
    debug(`sine `(s))
    ang += ASTEP
    waitms(2)
```

**How this works.** The third argument to `QSIN` is the number of steps in a full circle; passing **0** selects the native convention where the angle is the full 32-bit binary angle. `AMPL` scales the output, so the wave swings between `+AMPL` and `-AMPL`. Each loop advances the angle by `ASTEP` and emits one sample to the DEBUG `SCOPE`; a larger `ASTEP` is a higher frequency.

💡 **Tip:** For a *quadrature* pair (sine and cosine together — the basis of DDS and IQ work), Recipe 2's `ROTXY` trick gives you both from one rotation; or call `QCOS` alongside `QSIN` on the same angle.

🔍 **Verify:** The `SCOPE` traces a smooth sine wave peaking at **+1000** and **−1000**. At `ang = $4000_0000` (90°), `QSIN` returns **1000** and `QCOS` returns **0**; at `ang = 0`, `QSIN` is **0** and `QCOS` is **1000**.

## Recipe 5 — Fixed-Point Scale & Magnitude

**Use it when** you are doing arithmetic that overflows 32 bits or needs a fraction — scaling a value by a ratio, taking a magnitude, working in decibels — and you have no floating-point unit.

The CORDIC *is* the P2's wide-integer engine. Three idioms cover most fixed-point work: `MULDIV64` for `(a * b) / c` without overflow, QVECTOR for a magnitude that would overflow if you squared it yourself, and QLOG / QEXP for logarithms.

```spin2
CON
  _clkfreq = 200_000_000

PUB main() | a, b, c, scaled, mag, ang, lg, back
  a := 123_456
  b := 789_012
  c := 1000
  scaled := muldiv64(a, b, c)        ' (a*b)/c, 64-bit intermediate
  mag, ang := XYPOL(a, b)            ' sqrt(a*a + b*b), 64-bit-safe
  lg  := qlog_of(a)                  ' base-2 log, 5.27 fixed-point
  back := qexp_of(lg)                ' antilog round-trips back to ~a
  debug("scaled=", udec(scaled), "  mag=", udec(mag))
  debug("log2=", uhex_long(lg), "  back=", udec(back))

PRI qlog_of(v) : r
  org
    qlog v
    getqx r
  end

PRI qexp_of(v) : r
  org
    qexp v
    getqx r
  end
```

**How this works.** `muldiv64` multiplies `a` by `b` into a 64-bit intermediate (a QMUL) and divides by `c` (a QDIV fed the 64-bit product), so `123_456 * 789_012` never overflows on the way to the answer. `XYPOL` returns a vector's length, which is `sqrt(a*a + b*b)` computed with a 64-bit intermediate — the safe way to take a magnitude, since `a*a` alone would overflow. QLOG returns a base-2 logarithm in **5.27 fixed-point**: the top five bits are the whole part (the position of the value's most-significant set bit) and the low 27 bits are the fractional mantissa. QEXP is its inverse. The two short inline-PASM helpers expose QLOG/QEXP because Spin2 has no one-line method for them.

🔧 **Hardware — everything is unsigned.** QMUL, QDIV, QFRAC, and QSQRT treat their operands as *unsigned*. When your data is signed, take the magnitude first, remember the sign, and reapply it to the result. (Recipe 1 and Recipe 2 are already signed — QVECTOR and QROTATE handle signed coordinates.)

🔍 **Verify:** The output reads **scaled = 97,408,265** (which is `123_456 * 789_012 / 1000`), **mag = 798,612** (the length of the vector `(123_456, 789_012)`), **log2** whole part **16** (because 123,456 sits between 2¹⁶ and 2¹⁷), and **back ≈ 123,456** — the log/antilog round trip.

## Recipe 6 — Pipelining for Throughput

**Use it when** you have *many* values to transform and one-at-a-time is too slow — filtering a buffer, rotating a point cloud, scaling an array.

A single CORDIC result takes 55 clocks. But because the pipeline is 54 stages deep and a cog can issue every 8 clocks, you do not have to wait 55 clocks *per value*. Issue a batch of operations first (**fill**), then settle into reading one result and issuing one new operation each pass (**steady state**), and finally read out the stragglers (**drain**). Done right, you retire one finished result roughly every eight clocks.

This cog squares an array of values that way — a stand-in for any per-element CORDIC transform:

```spin2
CON
  _clkfreq = 200_000_000
  N    = 8                      ' elements to transform
  FILL = 6                      ' in flight (~6-7: 54-stage/8)

VAR
  long inbuf[N]                 ' source values
  long outbuf[N]                ' results (follow inbuf in hub)
  long done                     ' handshake flag

PUB main() | i
  repeat i from 0 to N-1
    inbuf[i] := 10 + i          ' 10,11,...,17
  done := 0
  coginit(NEWCOG, @square_engine, @inbuf)
  repeat until done
  repeat i from 0 to N-1
    debug(udec(inbuf[i]), " squared = ", udec(outbuf[i]))

DAT             org

square_engine
                mov     inp, ptra            ' @inbuf
                mov     outp, ptra
                add     outp, ##N*4          ' @outbuf
                mov     donep, ptra
                add     donep, ##N*8         ' @done
                mov     ii, #0               ' issue index
                mov     jj, #0               ' retire index

' Fill phase: queue FILL operations before reading any result.
.fill           cmp     ii, #FILL       wcz
        if_ae   jmp     #.steady
                cmp     ii, #N          wcz
        if_ae   jmp     #.steady             ' N < FILL: queue only N
                rdlong  t, inp
                add     inp, #4
                qmul    t, t                 ' queue: t*t
                add     ii, #1
                jmp     #.fill

' Steady state: retire one result, queue one more.
.steady         cmp     jj, #N          wcz
        if_ae   jmp     #.done
                getqx   r                    ' next result, FIFO order
                wrlong  r, outp
                add     outp, #4
                add     jj, #1
                cmp     ii, #N          wcz
        if_ae   jmp     #.steady             ' none left -> drain
                rdlong  t, inp
                add     inp, #4
                qmul    t, t
                add     ii, #1
                jmp     #.steady

.done           wrlong  #1, donep
                cogid   t
                cogstop t

inp             res     1
outp            res     1
donep           res     1
ii              res     1
jj              res     1
t               res     1
r               res     1
```

**How this works.** Two indices track the pipeline: `ii` counts operations *issued*, `jj` counts results *retired*. The fill phase issues `FILL` multiplies before reading anything, so `FILL` operations are in flight at once. Steady state then reads one result (GETQX, which returns results in issue order), writes it out, and — if any input is left — issues one more, holding the in-flight count steady. When the inputs run out, the same loop keeps reading until every result is drained. `FILL = 6` stays within the roughly seven operations the pipeline can hold.

⚠️ **Pitfall — protect a pipelined sequence from interrupts.** The 55-clock gap between issuing and retrieving is a window an interrupt can stretch, and a late read means a result is overwritten by the next one. In PASM2 with interrupts enabled, wrap the juggle in a REP block so the cog cannot be interrupted mid-sequence. Spin2 needs none of this — the interpreter already protects its CORDIC use.

🔍 **Verify:** The DEBUG window lists each input and its square — **10 → 100, 11 → 121, … 17 → 289**. The point is not the squares (a plain multiply would do that); it is that all eight flow through the solver overlapped, finishing in roughly the time of one operation plus eight windows rather than eight times 55 clocks.

## The Ceiling — Three-Phase Motor Control

The recipes above are foundations. To see them composed into a real product, look at **field-oriented motor control**, the technique behind quiet, efficient brushless and AC motor drives. Its mathematical core is the **Park transform**, which converts three phase currents into a rotating two-axis frame — and that transform is nothing but QROTATE operations.

The forward transform rotates three vectors (one per phase, 120° apart) and sums them. Written for the solver, it is three QROTATE issues with only a cheap angle adjustment between them — the same 120° offset expressed as the binary-angle constant `$5555_5555` — and then the results are read back and combined. It is Recipe 6's pipelining and Recipe 2's rotation in one real loop: the three rotations overlap in the pipeline instead of paying the 55-clock latency three times, and the 120° phase spacing is a modular add because the angle is a full-circle binary value.

This note does not rebuild that design — it is the ceiling, shown to make the point that the recipes here are the actual building blocks of production code, not toys. A complete, working Park/inverse-Park implementation by the P2 community (ManAtWork, **OBEX #2811**) is in the OBEX, listed in the Resources; reading it after this note, you will recognize every move.

## Going Further

**Feeding the streamer.** A common next step is to compute values with the CORDIC and *stream* them out a pin — direct digital synthesis, where a QROTATE or `QSIN` produces each sample and the streamer paces it to a DAC. The streamer is its own subsystem with its own timing; that composition belongs to the **Streamer Programming Guide**, which owns the streamer mechanics this note would otherwise have to duplicate. Use this note for the math, that guide for the streaming.

**When *not* to use the CORDIC.** The solver is fast, but it is shared and has a 55-clock latency. For a single occasional angle where you need an answer *this instant* and to a coarse tolerance, a small polynomial approximation can win — one P2 compass driver (**OBEX #5278**) deliberately computes `atan2` with a hand-tuned polynomial because, for its one-shot use, that beat queuing a CORDIC operation. The lesson is the general one: the CORDIC shines when you have a *stream* of operations to overlap, or need its full precision; for a lone, loose, latency-sensitive value, weigh the alternative.

## See It Work / Verify

Every recipe in this note shares the same kind of check, and it is stronger than a bench measurement: because the CORDIC computes deterministic math, the **expected answer is one you can derive by hand**, and a correct build must match it.

**What success looks like.** Each program streams a value — a distance, a coordinate, a waveform, an array — to a DEBUG window, and that value equals the closed-form result: `XYPOL(3, 4)` is 5; `ROTXY(100, 0, 90 deg)` is `(0, 100)`; `QSIN` of 90° at amplitude 1000 is 1000; `muldiv64(123_456, 789_012, 1000)` is 97,408,265.

**When it doesn't work:**

- **A result off in only its lowest bits.** Expected. The trigonometric operations carry about 28 bits of precision, so a value you predicted as exactly `(0, 100)` may read `(0, 99)` or `(1, 100)`. That is the engine's resolution, not a bug — see Pitfalls.
- **A wildly wrong or garbage result.** Almost always a sign or unsigned mistake (Recipe 5's note) or reading the wrong result register — GETQX is the X / length / quotient, GETQY is the Y / angle / remainder.
- **A read that returns instantly and sets the QMT event.** You read a result without issuing an operation first. Check that every GETQX / GETQY is paired with an earlier issue.
- **Nothing in the DEBUG window.** Build with DEBUG enabled (`pnut_ts -d`); without it the `debug()` directives are ignored.

## Pitfalls & Notes

⚠️ **Pitfall — the operations are unsigned where you might assume signed.** QMUL, QDIV, QFRAC, and QSQRT are unsigned. Mixing in a negative operand gives a huge positive one. For signed work, separate magnitude and sign, compute on the magnitude, and reapply the sign. (QVECTOR and QROTATE *are* signed — they are built for coordinates.)

⚠️ **Pitfall — read each result before the next overwrites it.** Each cog's results sit in a small pipeline; if you issue faster than you read, a result you never retrieved is lost. When pipelining (Recipe 6), keep the issued-minus-retired count within what the pipeline holds, and never let an interrupt stall a pipelined sequence (use REP).

💡 **Tip — the angle is the whole 32-bit range, so there is no wrap to manage.** Add or subtract angles freely; overflow is exactly the wrap-around you want. The common offsets are memorable as fractions of 2³²: 90° = `$4000_0000`, 120° = `$5555_5555`, 180° = `$8000_0000`, 240° = `$AAAA_AAAA`.

🔧 **Hardware — the CORDIC is shared, fairly.** All cogs use the one solver through the hub rotation; each cog gets a turn every eight clocks and cannot monopolize it or corrupt another cog's results. You never lock it or wait on another cog — but the 55-clock latency is fixed and does not shrink by using fewer cogs.

🔍 **Verify — precision is about 28 bits for trig, exact for integer ops.** Multiply, divide, and square root are exact (they are real 64-bit integer operations). Rotate, vector, sine, log, and exp are computed to roughly 28 bits, with the magnitude scale-factor corrected in hardware. Expect the low few bits of those to be approximate.

## Conclusion

The P2's CORDIC turns the math that usually dominates a small processor — trigonometry, rotation, wide multiply and divide, logarithms — into single operations with one shared, simple shape: queue it, do other work, retrieve it. Once that shape is in hand, the recipes are small variations on it: a vector becomes a distance and a heading, an angle becomes a point or a wave, a pair of numbers becomes a 64-bit-safe product or magnitude. And when there is a lot to compute, the same pipeline that imposes a 55-clock latency hands it back as one result every eight clocks. Reach for the CORDIC whenever your code is about to compute geometry or do arithmetic that overflows 32 bits — it is already there, in every cog, waiting for the next operation.
