# Chapter 2: Staying Inside the Debug Limits

Every debug build has limits, and a program that keeps adding debug output eventually meets them. This chapter is about meeting them on your terms: knowing where you stand, knowing what each kind of statement spends, and spending less without giving up the information you need.

The figures themselves are not in this chapter. They belong to the compiler, they can change from one release to the next, and the compiler reports them every time you ask.

## 2.1 Three limits, one listing

The compiler limits three things about a debug build:

- the number of distinct debug records in the program;
- the size of one record, which is the encoded data of a single statement;
- the total DEBUG data of all the records combined.

A record is what one `debug()` statement compiles to. When a cog reaches the statement, a `BRK` instruction selects that statement's record, and the debugger looks the record up and sends the message it describes. The records are stored with the debugger, at the top of hub RAM, rather than in your program's code.

To see where you stand, compile with `-d` and ask for a listing:

```command
pnut-ts -d -l myapp.spin2
```

The listing reports both totals, on the lines `DEBUG records:` and `DEBUG data:`, each with the current usage and the current maximum. Read the maximums there, from the compiler you are using, and never from a document, this one included.

Do not estimate DEBUG data from the size of the binary. The difference between a `-d` build and a plain build includes the debugger itself, which is present even when the program has no debug statements at all.

Without `-d`, the compiler ignores every debug statement and includes no debugger, so a release build needs no statements commented out.

## 2.2 When a limit is crossed

Past a limit, the build fails at compile time. The compiler stops with "DEBUG data is too long" and gives the reason: too many records, one record that exceeds its size, or a total that exceeds the maximum. Whichever it is, take the maximum from the listing.

The rest of this chapter is about not getting there.

## 2.3 What counts as DEBUG data

DEBUG data is the literal text inside `debug()` statements, the labels that the labelled output commands print, and an overhead for each statement.

The labelled commands print the source of what they show as well as its value: `debug(uhex(x))` prints something like `x = $ABC`. To print that label, the record stores the name `x`. Every output command also has a value-only form, whose name ends in an underscore (`udec_()`, `sdec_()`, `zstr_()` and the rest), which prints only the value and stores no name.

Strings kept in a `DAT` block are not DEBUG data. Printing one with `zstr_()` leaves only the command bytes in the record.

## 2.4 Moving text out of debug()

Here are two statements that carry their descriptive text inline:

```{.spin2 caption="ch02-text-inline.spin2"}
CON
  _clkfreq = 200_000_000

PUB main() | temp
  temp := 21
  debug("Sensor A temperature, degrees C: ", sdec_(temp))
  debug("Sensor B temperature, degrees C: ", sdec_(temp))
```

Move the text into `DAT` and print it with `zstr_()`, and the text leaves DEBUG data entirely:

```{.spin2 caption="ch02-text-in-dat.spin2"}
CON
  _clkfreq = 200_000_000

PUB main() | temp
  temp := 21
  debug(zstr_(@sSensorA), sdec_(temp))
  debug(zstr_(@sSensorB), sdec_(temp))

DAT
  sSensorA  byte  "Sensor A temperature, degrees C: ", 0
  sSensorB  byte  "Sensor B temperature, degrees C: ", 0
```

Compile both with `pnut-ts -d -l` and compare their `DEBUG data:` lines.

The move does more than save bytes. The value-only commands store no name, and `zstr_()` does not store the pointer it is given, so the two statements in the second version are identical and the compiler keeps one record for both. Compare the `DEBUG records:` lines as well.

The same move works for a whole line. Build the line in a hub byte buffer, from labels kept in `DAT` and digits your own code writes, and print it with a single statement:

```{.spin2 caption="ch02-line-buffer.spin2"}
CON
  _clkfreq = 200_000_000
  LINE_MAX = 80                 ' longest line, in characters

VAR
  long lineLen
  byte lineBuf[LINE_MAX + 1]    ' room for the terminating zero

PUB main() | count, errors
  count := 1_250
  errors := 3
  lineStart()
  lineText(@sCount)
  lineDec(count)
  lineText(@sErrors)
  lineDec(errors)
  lineEmit()

PRI lineStart()
  lineLen := 0
  lineBuf[0] := 0

PRI lineChar(c)
  if lineLen < LINE_MAX         ' never write past the buffer
    lineBuf[lineLen++] := c
    lineBuf[lineLen] := 0

PRI lineText(pStr)
  repeat strsize(pStr)
    lineChar(byte[pStr++])

PRI lineDec(value) | divisor, started
  divisor := 1_000_000_000      ' value must not be negative
  started := false
  repeat until divisor == 0
    if value / divisor or started or divisor == 1
      lineChar("0" + value / divisor)
      started := true
    value //= divisor
    divisor /= 10

PRI lineEmit()
  debug(zstr_(@lineBuf))        ' the whole line, one statement

DAT
  sCount   byte  "count=", 0
  sErrors  byte  " errors=", 0
```

The helpers are deliberately plain. `lineChar()` stops at `LINE_MAX`, so a line that runs long is cut short instead of running past the end of `lineBuf`, and `lineDec()` handles only values that are not negative. However many places in a program use `lineEmit()`, its one `debug()` statement is one record.

## 2.5 Fewer records

Each distinct `debug()` statement is a record, and the compiler merges statements that are byte-for-byte identical, wherever in the program they appear:

```{.spin2 caption="ch02-share-records.spin2"}
CON
  _clkfreq = 200_000_000

PUB main() | x, y
  x := 10
  y := 20
  debug("tick")                 ' a record
  debug("tick")                 ' identical, so it shares that record
  debug(udec(x), udec(y))       ' one statement, one record, two values
  debug(udec(x))                ' a different statement: a new record
  debug(udec(y))                ' stores the name "y": another record
```

The two `debug("tick")` statements share one record. Printing `x` and `y` from one statement takes one record, where printing them from two statements takes two. The last two statements look alike but are different records, because each labelled `udec()` stores the name of what it prints. Five statements, four records: the listing's `DEBUG records:` line shows it.

So there are two ways to spend fewer records: make statements identical, which the value-only forms make easy because they carry no name, and merge statements that report together.

Runtime controls do not help here. `DEBUG_COGS` and an `IF()` inside `debug()` decide at run time whether a message goes out, but the record is compiled either way.

## 2.6 Compiling less

The compile-time switches remove statements from the build altogether.

Setting `DEBUG_DISABLE` to any non-zero value removes every debug statement in the file that defines it.

For finer control, give each subsystem a channel. Define `DEBUG_MASK` in a `CON` block and write `debug[N](...)`: a statement on channel `N` is compiled only if bit `N` of the mask is set. Channels run from 0 to 31, and naming them with constants keeps the mask readable:

```{.spin2 caption="ch02-channels.spin2"}
CON
  _clkfreq   = 200_000_000

  CH_ERROR   = 0                ' one channel per subsystem
  CH_SENSOR  = 1
  CH_MOTOR   = 2

  DEBUG_MASK = (1 << CH_ERROR) | (1 << CH_SENSOR)

PUB main() | reading, speed
  reading := 512
  speed := 75
  debug("boot")                         ' plain: always compiled
  debug[CH_ERROR](zstr_(@sSelfTest))    ' bit 0 set: compiled
  debug[CH_SENSOR](udec(reading))       ' bit 1 set: compiled
  debug[CH_MOTOR](udec(speed))          ' bit 2 clear: not compiled

DAT
  sSelfTest  byte  "self-test passed", 0
```

Two rules come with channels. A plain `debug()` statement, with no channel, is not controlled by the mask at all: it is compiled in every `-d` build that `DEBUG_DISABLE` has not switched off, even when `DEBUG_MASK` is 0. And `debug[N]()` needs `DEBUG_MASK` to be defined; without it, the build fails. Keep plain `debug()` for the few lines that must always print, such as a boot message or a fatal error, and put everything else on a channel. Channels need no version directive.

The mask belongs to the file that defines it, so a parent's mask does not reach a child object, and a child that defines `DEBUG_MASK = 0` adds no records and no DEBUG data. A parent can still turn a child's channels on, by setting the child's mask where it declares the object:

```{.spin2 caption="ch02-sensor-driver.spin2"}
CON
  CH_TRACE   = 0
  DEBUG_MASK = 0                ' silent unless the parent sets it

PUB sample(value) : result
  result := value * 2
  debug[CH_TRACE](udec(value), udec(result))
```

```{.spin2 caption="ch02-light-a-child.spin2"}
CON
  _clkfreq = 200_000_000

OBJ
  sensor : "ch02-sensor-driver" | DEBUG_MASK = %1   ' channel 0 on

PUB main() | reading
  reading := sensor.sample(21)
  debug(udec(reading))
```

Records belong to the whole program. Once the child's channel is on, its statement counts against the same totals as the parent's: build `ch02-light-a-child.spin2` with and without the override and compare the listings.

A reusable object should not spend its user's limits by default. Set `DEBUG_DISABLE = 1` in it, or put its statements on channels and document which channel is which.

## 2.7 Keeping a margin

Treat the listing's maximums as ceilings, not targets. A program that compiles right at a maximum has no room for its next statement, and a newer compiler may draw the limits differently. Watch both listing lines as the program grows, and apply the techniques in this chapter before you need them.

Chapter 3 takes these techniques into a large program, and Chapter 11 covers what else a debug build takes from the program it is built into.
