# P2 Hardware-Verification Evidence

**What this is.** The repository of **empirically-established P2 facts** — behaviors
we proved by building a test, running it on real P2 silicon (or the PNut /
PNut-Term-TS toolchain), capturing the output, and analyzing it. It is the durable,
citable home for:

- **Tests we built** — the `.spin2` stimulus programs (tracked).
- **Test results** — the captured DEBUG output, quoted verbatim into the analysis.
- **Logs gathered** — small result logs are quoted here; large raw captures
  (`usb-traffic*.log`, multi-MB) are NOT tracked (see `.gitignore`).
- **Our analysis** — a running ledger of what each test established, kept as
  **golden source material** that future YAML/manual updates cite.

## Why this exists — a new tier in the trust chain

The project trust chain is **Trusted Sources → Trusted YAML → Trusted Documentation
→ Community.** Hardware verification is a **first-class trusted source** — distinct
from the documentary sources in `engineering/ingestion/` because it is *empirically
generated*, not extracted from a document. It is the strongest evidence we have:
when a test runs on silicon, the chip itself is the authority.

This evidence has repeatedly **overturned documentary claims**: Titus was wrong on
the async-TX first-byte glitch (RA-19), our own YAML was wrong on smart-pin %00101
Y=0 (F-135), and a released manual example didn't render (F-138). Documents can be
wrong; a clean hardware run is ground truth. That is why this evidence must be
**durable and tracked** — historically it lived in git-ignored scratch folders,
which is backwards for our most authoritative material.

## Lifecycle: workspace → replicated source of truth

Tests are **built and run in the manual workspace** where the work is happening —
`engineering/document-production/manuals/<manual>/audit/verification-tests/` (git-ignored).
That workspace is where a test is authored, compiled, flashed, and the raw logs land.
**Those copies are workspace + history, NOT the source of truth.**

When a test is **run and its result accepted**, it is **replicated here** — the
`.spin2` source and the analysis (ledger entry) — and *this* copy becomes the source of
truth. The flow:

```
build + run + accept (manual workspace)  ──replicate accepted──▶  here (golden source)
   .spin2, .bin, raw logs (transient)                              .spin2 + analysis (versioned)
```

- **We version the source** (the `.spin2` stimulus) and **the interpretation of the
  source** (the ledger entry — the golden reading of what it proved).
- **We do NOT version the raw logs.** They are left side-by-side in the workspace; if ever
  lost they can be regenerated by recompiling the versioned source and re-running.
- The workspace copy may keep evolving; only an **accepted** result is replicated here. A
  divergence between the two is expected — the workspace is live, this is the accepted record.

## How to use it

- **Grounding a YAML or manual edit?** Cite the relevant entry in
  [`P2-EMPIRICAL-FINDINGS.md`](P2-EMPIRICAL-FINDINGS.md) (e.g. "universal smart-pin
  init order — verified, campaign 2026-06"). The corrections register
  (`engineering/operations/P2KB-CORRECTION-FINDINGS.md`) cross-references here for
  the *evidence*; this tree holds the *proof*, the register holds the *to-fix*.
- **Reproducing a result?** The test program is under the campaign's `tests/`;
  compile with `pnut-ts -d <file>.spin2` (the `-d` is mandatory for DEBUG-window
  programs or the compiler ignores `debug()` contents). Flash the `.bin` to a P2.
- **A claim contradicts a ledger entry?** The ledger wins for what was *observed*,
  but note the entry's date + tooling version — silicon behavior is stable, but a
  host-tool (PNut-Term-TS) behavior may have since been fixed.

## Structure

```
engineering/ingestion/external-sources/hardware-verification/
  README.md                  # this file
  P2-EMPIRICAL-FINDINGS.md   # THE running golden-source ledger (cross-campaign)
  campaigns/
    <YYYY-MM-topic>/
      README.md              # campaign scope, rig, tooling, test roster + verdicts
      tests/                 # the .spin2 stimulus programs (tracked)
```

## Conventions

- **One ledger, many campaigns.** A *campaign* is a dated investigation (a sprint of
  related tests). The ledger is the cross-campaign index of durable facts; each fact
  points back to the campaign + test that established it.
- **Tracked:** `.spin2` tests, all `*.md` (campaign READMEs, analysis, the ledger).
- **NOT tracked:** `*.bin` (regenerable via `pnut-ts`), `usb-traffic*.log` and other
  multi-MB raw captures. Quote the *salient* output into the analysis instead.
- **Rig honesty.** Every entry records HOW it was observed (real wired loopback vs
  internal pin routing vs own-pin IN flag) and on WHAT (real P2 vs PNut vs
  PNut-Term-TS). A NOT-OBSERVED on a real wire is a stronger negative than an
  internal-routing one — say which.
- **Disproven findings count.** "We tested X and it's NOT true" is as valuable as a
  confirmation — record it (it stops the claim being re-introduced).
