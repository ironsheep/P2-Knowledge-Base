# p2-debug-techniques — claim ledger

Every claim in the three source files, one atomic row each, with its kind, the KB's current
status, how it is verified, and where it goes. Built 2026-10-12 («#427») by five fresh extraction
agents over disjoint sections, merged by the arbiter, who ran the container checks in the
**arbiter** column himself on pnut-ts 1.55.8. A row is a **claim from a lead**, not a fact:
nothing here reaches the KB or a document until its route is run.

**Columns.**
- **kind:** fact (true of the P2, Spin2 or toolchain) · technique (a composable method) · trap
  (legal code or setup that silently does something else) · method (engineering discipline).
- **KB status:** checked against `deliverables/ai/P2/` at KB v1.24.7.
- **verify route:** container (pnut-ts / listing) · source (an ingested Parallax document) ·
  XF (a partner-bench measurement, graded in «#429») · bench (needs silicon, no measurement) · n/a.
- **destination:** YAML · HB-output / HB-rig / HB-trust (the diagnostics handbook's parts) ·
  P2AN006 · IOSP-guide · Streamer-guide · PNutTerm-guide · AntiPatterns · Spin2Ref ·
  SSDebugger-manual · GENERIC-method (Stephen: consider separately) · drop.

**KB statuses are the agents' readings.** Every CONTRADICTS is hand-checked before anything
changes, because fan-out findings can be inverted. Agent ref letters are kept so each row traces
to its extraction part.

### Part B — extraction notes

#### Notes

1. **B-43 is contested.** `spin2-v55-text.txt:286` ("Results and local variables are initialized to zero on method entry"; also changelog v37 line 29, "Spin2 local variables now get zeroed upon method entry") and the KB's own `cogspin.yaml` growth text (call "clears to zero") mean pure-Spin2 frames write every parameter/result/local long. A zero is not the sentinel, so such longs count as touched and no hole arises from locals or results. The source's example, "a frame that reserves longs it never writes", is therefore not shown for pure Spin2. Holes could still arise from the frame/return-address layout or inline PASM, and the source's observation was labelled [measured], but I found nothing in the KB or Parallax text that supports it. 2. **B-52 / `_STACK`,`_FREE` inert.** KB `cogspin.yaml` already says so. `spin2-v55-text.txt` has no `_STACK` or `_FREE` text (grep found none), so the "[documented]" tag is not backed by v55; it rests on the source's own md5 comparison. #### Disagreements between the two files (and against the KB)

1. **Whether debug[N]() needs `{Spin2_v46}`.** GEN §1.1 says it needs none and older guidance saying so is wrong. DEV does not state that it needs the directive. It says only that DEBUG_MASK was "introduced in PNut/pnut-ts v46". GEN is right. v55 line 38 (v46 changelog: "DEBUG gating and disabling added", defining DEBUG_MASK and `DEBUG[bitnumber]`) gives no directive. The v55 version-gated keyword table (line 148) lists `{Spin2_v46}` only against the C_Z debug command. The KB itself disagrees internally: `language/spin2/constants/debug-mask.yaml:16,124` and `special-configuration-symbols.yaml:538` say no directive; `language/spin2/debug-commands/debug-strategy-guide.yaml:172,233,252,269,348,370` still say it is required. That stale guide is the actual source of the "older guidance".
2. **COGSTOP and held locks.** DEV §7.1's original text (and DEV §8's table row: "COGSTOP releases a held lock, contradicts the published COGSTOP page") reads as a binary release/not-release finding. The DEV §7.1 box says this is superseded in part: the state clears, the allocation leaks. GEN §14 and the KB (`cogstop.yaml:72-74`, `locks.yaml:50-72`) agree with the superseded version. DEV's "the published documentation says the opposite" is wrong about the primary source. The silicon doc says "implicitly released" when the holding cog is stopped (`engineering/ingestion/sources/silicon-doc/silicon-doc-text.txt:3698`, `p2-documentation.txt:7488`). v55 has no lock statement under COGSTOP (line 518 only: "Stop cog CogNum."). The contradiction was with a former P2KB COGSTOP page, which the KB has since corrected. DEV §8's table row is stale against its own §7.1.
3. **Stack scan direction in the source utility.** DEV's header and §4.2 table say `isp_stack_check.getStackDepth()` scans upward, and flag themselves stale. GEN §7.3 and `application-notes/p2an006-sizing-cog-task-stacks.yaml:76` say downward. GEN and the KB are right; DEV §4.2's table is wrong. The principle (downward is correct) is the same in both.
4. **Strength and scope of the 16 KB claim.** DEV §1.1 states the cap as "16 KB across the whole program" and a breach as silent, with no compile error. GEN §2 separates the records limit (255, fails the build) from the bytes budget (16,384 documented, silent, usable ceiling below it: 13,332 ran, 15,347 died). GEN also says to gate builds at the highest measured value. GEN is the more precise; DEV states the headline only. v55:897-901 supports only the 16 KB region, not the cap behaviour.
5. **KB against both files, on silence.** `debug-strategy-guide.yaml:40-44` says exceeding the DEBUG data maximum fails the build (m151). DEV and GEN say the bytes budget breach is silent on hardware. These can both be true if the silent band sits below the compile-time maximum, as GEN's dose-response suggests. The KB does not say so. Needs a container check (compile an oversize program with `pnut-ts -d -l`) and the bench figures.
6. **KB against both files, on overriding DEBUG_MASK.** DEV §2.2 and GEN §1.1 both say it cannot be overridden at instantiation (GEN: `Expected a symbol`). `debug-strategy-guide.yaml:243-249` says the parent can set the child's mask. Check by compiling an OBJ override; v55 is silent.
7. **KB against both files, on -D equivalence.** `pragma-exportdef.yaml:11` says the export acts "exactly as if -D SYMNAME had been given on the command line". DEV §3.3 and GEN §11.4 say -D is visible in the declaring file and exportdef is not. `pragma-exportdef.yaml:35` already says the exporting file must also #DEFINE it. Line 11 is the overstatement.
8. **Mechanism for the dead debug channel after a stop.** DEV §2.5 offers a candidate (the -d build gives the driver cog a debug interrupt via the all-cogs default); GEN says only "no mechanism established". Not a conflict; DEV is more specific and unmeasured (see E-23).
