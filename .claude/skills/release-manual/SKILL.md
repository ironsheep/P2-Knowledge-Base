# Release Manual

You are promoting a P2 manual release from the development area to the public deliverables area. The PDF has already been placed by the user (after PDF Forge generation). This skill copies the CHANGELOG up and updates the public release index.

## Repo layout

```
engineering/document-production/manuals/<slug>/opus-master/
└── CHANGELOG.md                                  # SOURCE — copy this up

deliverables/documents/DOCs/
├── <DocName>.pdf                                 # User places this manually after Forge
└── <slug>-changelog.md                           # DESTINATION — copy CHANGELOG to here

deliverables/documents/README.md                   # Public release index — update version + date
```

## Step 1 — Identify the manual

Accept slug as argument. If absent, list manuals that have:
- A `manuals/<slug>/opus-master/CHANGELOG.md`
- A corresponding entry in `deliverables/documents/README.md`

Ask user which one to release.

## Step 2 — Parse the new version from CHANGELOG

Read `manuals/<slug>/opus-master/CHANGELOG.md`. Parse the **topmost** entry:
- Heading: `## v<X.Y.Z> (<YYYY-MM-DD>)` (handle both `v2.3.0` and `v2.3` forms — normalize to semver with `.0` appended if patch missing, per the project convention that `deliverables/documents/README.md` always uses three-part semver)
- Date: convert ISO `YYYY-MM-DD` → `Month Year` (e.g., `2026-05-23` → `May 2026`)

These become the new "Version" and "date - Community Review Edition" lines in the README.

## Step 3 — Verify PDF is present

Look up the manual's PDF filename. Two ways to find it:
- Read `engineering/document-production/workspace/<slug>/request.json` → `documents[0].output`
- Or read `deliverables/documents/README.md` and find the existing entry's PDF link (`[Title](DOCs/<PDF>)`)

Check `deliverables/documents/DOCs/<PDF>` exists. If absent:
- Stop. Report: "PDF not found at `<path>`. Generate the PDF via PDF Forge and place it at this path before running release-manual."

If present, report its size and modtime so the user can sanity-check it's the new one (not a leftover).

## Step 4 — Recommend (don't enforce) a changelog audit

If `audit-changelog` hasn't been visibly run on this manual recently, mention it:
> "Recommend running `/audit-changelog <slug>` first to verify the CHANGELOG is release-ready. Proceeding without it is OK if you've already audited."

Do NOT auto-invoke audit-changelog. Do NOT block the release. The user controls whether to run it.

## Step 5 — Show the plan and confirm

Use `AskUserQuestion` to show:
- Version being released: `<vX.Y.Z>` from CHANGELOG
- Date being stamped: `<Month Year>`
- PDF being promoted: `<path>` (size, modtime)
- CHANGELOG being copied: `<src>` → `<dst>` (line count of new entry)
- README sections being updated: show the BEFORE/AFTER for the two lines

Offer: proceed / cancel.

## Step 6 — Execute

1. **Copy the CHANGELOG**:
   ```bash
   cp manuals/<slug>/opus-master/CHANGELOG.md \
      deliverables/documents/DOCs/<slug>-changelog.md
   ```

2. **Update `deliverables/documents/README.md`** — find the manual's section by matching `(DOCs/<PDF>)` in a markdown link. From that anchor:
   - Find the next `*Version X.Y.Z*` line within ~10 lines below → replace with new semver-normalized version
   - Find the next `*<Month> <Year> - Community Review Edition*` line within ~15 lines below → replace with new date

   Use `mcp__filesystem__edit_file` for the edits — the existing surrounding text (title, subtitle, description prose, "Community Review Edition" suffix) is preserved exactly.

   If existing entry doesn't match the expected pattern, stop and ask user how to handle (don't guess).

## Step 7 — Enclosing-doc audit (verification, not auto-edit)

After Step 6's narrowly-scoped edits are applied, sweep the repo for stale references the release-manual edits don't catch. This is verification — surface candidates to the user, do NOT auto-edit. Broader docs (top-level README, repo CHANGELOG, other deliverables READMEs) need explicit user authorization per CLAUDE.md.

Run these searches scoped to the repo, excluding paths already updated in Step 6, opus-master sources, and backup files:

```bash
# Old version string of the manual being released
grep -rn "Version <PRIOR_VERSION>" --include="*.md" \
  | grep -v "deliverables/documents/DOCs/" \
  | grep -v "\.backup\." \
  | grep -v "engineering/document-production/manuals/.*/opus-master/CHANGELOG.md"

# Old date string being replaced
grep -rn "<PRIOR_DATE> - Community Review" --include="*.md" \
  | grep -v "\.backup\."

# Manual name in any README (might mention version in surrounding text)
grep -rln "<MANUAL_NAME>" --include="README.md" \
  | grep -v "engineering/document-production/"
```

Classify each non-trivial match:
- **Top-level repo docs** (`README.md`, `CHANGELOG.md`, `CLAUDE-QUICKSTART.md`) — candidate for update; surface to user
- **Other deliverables READMEs** (e.g., `deliverables/README.md`, `deliverables/ai-reference/README.md`) — candidate; surface
- **Internal engineering docs** (`engineering/**`) — usually filenames or sample text, not stale release references; surface only if version is in the matched text itself

Report findings tightly:
```
Enclosing-doc audit:
- <PATH:LINE> — <verbatim match (truncated to one line)>
- ...
[N candidates found; user decides which to update before commit]
```

If zero matches: report "Enclosing-doc audit: clean."

**Do not edit these files.** The user has visibility into the candidates and can either ask you to update specific ones (which then becomes a follow-up user instruction) or make the updates by hand. The release-manual scope is the deliverables release-index README and the changelog copy — nothing else.

## Step 8 — Report and suggest git commands

End with:
- What was copied (CHANGELOG)
- What was edited (README lines, with line numbers)
- Enclosing-doc audit results (from Step 7) — list of candidates the user should review
- Suggested git commands (do NOT execute):
  ```
  git add deliverables/documents/README.md \
          deliverables/documents/DOCs/<slug>-changelog.md \
          deliverables/documents/DOCs/<PDF>
  git commit -m "Release <slug> v<X.Y.Z>"
  git tag -a <slug>-v<X.Y.Z> -m "<Manual Name> v<X.Y.Z>"
  ```
- Tell user: "Review the diff, then run those commands when ready. Tagging gives audit-changelog a baseline for the next release."
- If the enclosing-doc audit surfaced candidates: tell user to decide on those before committing, so the git commit captures everything in one logical release.

## What this skill does NOT do

- Does not generate the PDF (PDF Forge does that)
- Does not place the PDF in DOCs/ (user does that manually)
- Does not edit `opus-master/CHANGELOG.md` (audit-changelog audits; user edits content)
- Does not run `git add` / `git commit` / `git tag` (per CLAUDE.md, git actions need explicit user authorization)
- Does not push to remote
- Does not auto-edit any markdown beyond `deliverables/documents/README.md` (top-level `README.md`, repo `CHANGELOG.md`, `deliverables/README.md`, AI-reference READMEs, engineering docs are all out of scope). Step 7's enclosing-doc audit *surfaces* candidates in those docs but does not modify them — the user decides what (if anything) to update there.

## Error handling

- PDF missing: stop with clear instruction (Step 3)
- CHANGELOG missing: stop — there's nothing to release
- CHANGELOG topmost entry has the same version as already-published (`deliverables/documents/README.md`): stop and ask — is this a re-release? Refusing-by-default avoids silent overwrites.
- README pattern doesn't match (existing entry has unexpected structure): stop and ask user how to handle; do not guess line positions
- Multiple `(DOCs/<PDF>)` matches in README: stop — ambiguous; ask user to clarify

## Tool preferences (per CLAUDE.md)

- Filesystem reads/edits → `mcp__filesystem__*`
- File copies + git commands → Bash
- Use `mcp__filesystem__edit_file` for the README updates (not `sed`/`echo`)
